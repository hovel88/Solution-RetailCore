# Анализ текущего состояния — RetailCore

Этот документ фиксирует текущее состояние системы,каким оно реально является, со всеми дефектами, зависимостями и обходными путями.  
Каждая находка опирается на первоисточник (например, цитату из стенограммы интервью), что обеспечивает трассируемость и защиту от искажений.  
Он будет являться основой для будущего TO-BE, чтобы спроектировать целевую архитектуру, понимая, где сейчас находится источник боли и какие связи нельзя порвать.

---

Основной документа являются стенограммы интервью с разработчиками, выдержки из исходников кода монолитного ядра системы. Кроме того, из контекста Task1 (бизнес + поддержка) будут привлечены как минимум некоторые ограничения, релевантные для разработки.

#### 1.2.2. Ключевые выводы

Монолитное ядро накопило критическую массу ответственности за разнородные функции (цена, промо, статусы, логистика, платежи), логика которых размазана по коду, Oracle-процедурам и конфигам, и скрывает в себе очень сильную связность.

**Рекомендации**:

- Начать с выноса слабо связанных функций (чтение статусов, часть промо, отдельные интеграции, post-order processing)
- Не трогать core order create и payment orchestration

#### 1.2.2. Ключевые выводы

Ключевая проблема в том, что логистический контур представляет собой набор неструктурированных интеграций без единого стандарта, без единого источника правды, без единого контракта статусов и логики выбора маршрута.

**Рекомендации**:

- Начать с унификации событий и контракта статуса доставки
- Убрать обмен данными между сервисами через БД
- Выделить и вынести логику выбора маршрута

## 7. Резюме

RetailCore — это легаси-система, которая:

- **Работает**, но на пределе связности и производительности
- **Держится** на монолите + Oracle + "племенных знаниях"
- **Имеет** критические архитектурные дефекты: размазанная логика, отсутствие единого источника правды, слабая наблюдаемость
- **Требует** поэтапной трансформации с осторожностью в критичном контуре

**Главный вывод**: проблемы аналитики, логистики и монолита — это проявления одной и той же проблемы: отсутствие чётких границ, единых контрактов и канонической модели данных.
