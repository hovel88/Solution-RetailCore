## 1. Цель переключения

Цель переключения — **включить наблюдаемость (correlation ID, метрики, трейсы)** на 5 пилотных магазинах. После переключения система должна **позволять собрать полную цепочку по заказу** через correlation ID, а метрики **время разбора инцидента** и **доля успешных трейсов** должны быть в пределах порогов. Старый контур (без correlation ID) сохраняется как fallback до завершения периода наблюдения.

## 2. Объём переключения

### 2.1. Включаем

- correlation ID на 5 пилотных магазинах
- метрики по критичному контуру пилота
- трейсы для заказов на пилоте
- дашборды для команды

### 2.2. Не включаем

- остальные магазины
- core order create и payment orchestration — не трогаем
- полная переработка логирования
- distributed tracing (OpenTelemetry) для всех систем

### 2.3. Критерии успешного переключения

| Критерий | Целевое значение | Где проверяем | Кто подтверждает |
| -- | -- | -- | -- |
| Покрытие correlation ID | >80% заказов на пилоте | Мониторинг | Tech Lead |
| Время разбора инцидента | -50% от baseline | Service Desk | Head of Support |
| Доля успешных трейсов | >80% | Мониторинг | SRE |
| Ошибки в логах | Не выше baseline | Мониторинг | SRE |

## 3. Условия запуска: go / no-go

> Переключение можно начинать только при выполнении входных условий. Если хотя бы одно критичное условие не выполнено, решение должно быть `no-go`.

| Условие | Тип | Как проверяем | Порог / ожидаемое состояние | Статус | Ответственный |
| -- | -- | -- | -- | -- | -- |
| Correlation ID развёрнут на пилоте | Техническое | Проверка деплоя | Все компоненты обновлены | go / no-go | Tech Lead |
| Мониторинг работает | Наблюдаемость | Дашборды + алерты | Метрики доступны | go / no-go | SRE |
| Тестовый заказ с correlation ID | Техническое | Прогон тестового заказа | Полная цепочка собрана | go / no-go | Tech Lead |
| Rollback протестирован | Техническое | Прогон отката | Откат <5 мин | go / no-go | SRE |
| Поддержка проинформирована | Коммуникация | Инструкции | Поддержка знает, что делать | go / no-go | Head of Support |
| Ответственный на связи | Операционное | Проверка доступности | Head of Order Management на связи | go / no-go | Дмитрий (бизнес-владелец) |

## 5. Состояние данных до переключения

> Cutover должен учитывать не только включение кода, но и состояние данных: какие данные уже подготовлены, какие синхронизируются, какие остаются источником истины.

| Данные / сущность | Источник истины до переключения | Источник истины после переключения | Подготовка до cutover | Проверка консистентности | Что делаем при расхождении |
| -- | -- | -- | -- | -- | -- |
| Заказы | Монолит | Монолит | Нет изменений | Не нужно (данные не мигрируют, только логи) | — |

## 13. Проверка качества cutover-плана

Перед сдачей проверьте, что:

- [ ] указано, что именно переключается и в каком объёме;
- [ ] есть go / no-go условия;
- [ ] роли и ответственность не описаны общими словами, а привязаны к действиям;
- [ ] сценарий переключения пошаговый и проверяемый;
- [ ] состояние данных до, во время и после переключения описано отдельно;
- [ ] есть наблюдаемость: метрики, дашборды, алерты, владельцы;
- [ ] новый контур сравнивается со старым через конкретные сценарии и пороги;
- [ ] rollback включает код, маршрутизацию, данные, очереди, статусы и коммуникацию;
- [ ] есть критерии стабилизации после переключения;
- [ ] по итогам cutover можно принять решение о продолжении roadmap.
